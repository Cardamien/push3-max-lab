# Notes for ableton-push-hack: corrections and additions from a tethered probe (Live 12.4.15, firmware 1.5.4)

For the docs of [federico-pepe/ableton-push-hack](https://github.com/federico-pepe/ableton-push-hack). Written as proposed edits, file by file.

Pinned to commit `be16956083a1ac4f9a59b5c30ae8e8d07023dac8`.

**Context.** Measured on 2026-10-30 from a Mac (macOS 15.7.4) running Live 12.4.15, with a Push 3 Standalone (firmware package 1.5.4, XMOS 1.0 build 91, board revision 3) attached by USB in Control Mode, plus the device's LAN services (`push.local`) and the strings, symbols and embedded Python constants of Live's `Helpers/Push3.app`. No root on the device, nothing installed on it; everything below that concerns the device's own OS internals is left to your SSH-based docs. Evidence classes: MIDI (CoreMIDI capture), USB (IOKit registry), HTTP, mDNS, LOG (Live's `Push3.log`), PYC (constants of the helper's Python bytecode), STRINGS (helper binary).

## Additions

Documentation patches the repo could carry, in the same files.

1. **`docs/push3-internals.md`, SysEx section: Push 3 command table.** Header `F0 00 21 1D 01 01 <cmd> ... F7`. Ids from `Push2/sysex.pyc` in Live 12.4.15: `0x0A` MODE_SWITCH (0 Live, 1 User); `0x20` PAD_VELOCITY_CURVE (chunks of 16); `0x26` SET_PAD_PARAMETER (`26 07 <pad> <value> 00`, the most frequent host message); `0x37` SET_AUDIO_CONTROLS; `0x38` GET_AUDIO_CONTROLS (request lists control ids, reply repeats each id followed by two value bytes; an empty request gets no reply); `0x39` POWER_COMMAND; `0x3A` GET_POWER_STATE; `0x3B` SET_ARBITRARY_RGB_LED_COLOR (`3B 00 <led> r_lo r_hi g_lo g_hi b_lo b_hi`); `0x3E` GET_HOST_MODE; `0x42` GET_FIRMWARE_UPDATE_RESULTS; `0x43` GET_PAD_VELOCITY_CURVE. Audio-control ids: `0x0D` SAMPLE_RATE, `0x18`/`0x19` ADC_OVERFLOW_CH_0/1, `0x1E` DAC_VOLUME_MASTER, `0x3A` EXT_SAMPLE_RATE, `0x3B` EXT_CLOCK_VALID, `0x3C` EXT_CLOCK_SEL. Touch-strip config ids `0x0C/0x0D/0x0E` (X axis output type, CC, relative down position) and `0x1A/0x1B/0x1C` (Y axis). Push 2 commands still in use: `0x03` set palette entry, `0x05`, `0x06` LED brightness, `0x08` display brightness, `0x17` touch-strip config, `0x19` touch-strip LEDs, `0x1E` aftertouch mode (third byte `02` = MPE on Push 3).
2. **Same section: power-button flow.** The short press you logged (`3A 2A 64`) is `0x22 | 0x08`: the SHORT_POWER_BUTTON_PRESS flag in the polled power state. The Push3 app shows the dialog on that flag and then sends `39 02` (CLEAR_SHORT_PRESS); a long hold sets `0x10` and is cleared with `39 05`. This is why no evdev or `.shutdown` activity precedes the dialog.
3. **Same section: identity reply.** `F0 7E 7F 06 01 F7` on the Live Port is answered `F0 7E 01 06 02 00 21 1D 69 32 03 00 01 00 5B 00 <serial, five 7-bit little-endian bytes> 03 01 14 04 F7`: family 0x3269, member 3, firmware 1.0 build 91 (0x5B), board revision 3, `01 14` = pmc firmware 1.20, trailing `04` unassigned.
4. **Push3 process architecture: the Mac helper is the same program.** `Live.app/Contents/Helpers/Push3.app` is the device's `Push3` built for macOS: same 19 command-line options (`--faceless`, `--no-parent`, `--log-to-syslog` marked linux-only, `--webservice-id-file`), the same cpp-httplib web service with 48 `/api/v1` routes compiled in, the same flip/nanomsg channels, the same CPython 3.11.6 `Push2` script package (243 modules, no `Push3` package) and the firmware blobs under `Push2/firmware/push3/push3_fw_1.5.4/` (xmos 1.0.91, imagery 0.7, pmc 1.20, xy 0.13, apc 1.9). On the Mac, D-Bus is replaced by an in-process `MockPush3DBusClient`/`MockPush3DBusServer` pair and the updater by `MockSWUpdateApi`; it logs "Skipping firmware update, not running standalone but compute module is installed". Anyone without SSH can study the device program on a Mac.
5. **Web service (`PushWebServiceCli`) from the LAN.** Every `/api/v1` request without credentials answers `401 {"error":"Unset credentials"}`; the header `Ableton-Challenge-Response-Token` authenticates. In Control Mode `POST /api/v1/challenge` fails with a D-Bus `ServiceUnknown` error for `com.ableton.push3`: pairing is relayed to the Push3 app, which is only on the bus in Standalone Mode. Pairing and the read-only routes are described in `../standalone/web-service.md`.
6. **Flip API payload (your open item).** The `push-flip-api-ipc-channel` carries Ohm Force's `flip` collaborative-document protocol (`flip::Transaction`/`Message` over a `NanoMsgFlipCarrier`); the shared document is `ableton::push_live_model` (`Root`, `Song`, devices, and RPC-style services `BrowserServices`, `MidiServices`, `AudioServices`, `LicenseServices`, `M4lServices`, `RealTimeServices`, each with `Message_<name>_call`/`_response`). Real-time data (waveforms, playhead, images, count-in) does not go through flip but through boost::interprocess shared memory named `RTC_Waveform`, `RTC_Playhead`, `RTC_Image`, `RTC_CountIn` plus a UUID.
7. **USB topology, seen from the host.** The Mac sees hub 0x0424:0x2534 (bcdDevice 0x0182) with the Ableton device 0x2982:0x1969 (bcdDevice 0x0100, composite, high speed, self-powered 0 mA) on hub port 4, the same port number as your internal `1-1.4`. Consistent with your hub/mux hypothesis for the mode switch; not a proof.
8. **Display sync transfers.** The `F8 F8 13 13 <cmd> 00 00 00 <sub>` transfers are commands: `0a` queries system info (engineering run, flash lock, compute module, battery, serial, uptime, firmware package version) and `01 <sub>` with sub `06 08 07 00 09` queries the pmc, apc, xySensor, startupImage and imagery versions; each is answered by 40 bytes on endpoint 0x81. The frame stream runs at about 48 frames/s from the Mac helper.

## Answers to open items

- **Battery section, "no publicly documented SysEx command byte values":** `0x3A` GET_POWER_STATE and `0x39` POWER_COMMAND, formats above; readable by any MIDI client on the Live Port, no root and no Python environment needed. Open: the charging-state enum values in the low bits (our unit was at 100 % on mains: `0x22`).
- **"No web ports open by default" row:** port 80 is open and advertised on firmware 1.5.4 in Control Mode. Open: whether it is open on your firmware and settings; `ss -ltnp` on the device would name the listener (`PushWebServiceCli` expected).
- **Interface table rows 1-4:** 1 is the UAC2 audio control, 2 and 3 are the streaming interfaces (OUT and IN), 4 is the UAC1 control of the MIDI function paired with 5. Row 6 stays unknown; battery and LEDs are not its job.
- **Power-button section, "command byte `3A` is not in any public Push 3 documentation" and the long hold:** `3A` is GET_POWER_STATE; a long hold should set bit 0x10 (not observed by us).
- **IPC sockets, "flip-API payload undecoded":** see addition 6.
- **Interface 6 / `xPort`, MIDI on `ep_03`/`ep_83` from the libusb hook:** untestable from a tethered Mac (no interface 6 access attempted). For the hook question, the Mac build does MIDI through CoreMIDI and uses libusb for interface 0 only, which supports your internals text by analogy; the device-side disagreement with `push_hook.c` stays yours to settle.

## Addendum, Standalone Mode (same day, paired)

- `docs/push3-internals.md` System table: add CPU `11th Gen Intel Core i3-1115G4 @ 3.00 GHz` (4 logical CPUs), board `Intel Client Systems CM11EBI38W` (NUC 11 Compute Element), BIOS `EBTGL357.0068.2022.0531.1726`, memory 7665712K usable of 8002460K; kernel built with x86_64-oe-linux-gcc 12.2.0 on 2022-06-21. Evidence: the device's own `syslog/current` via the web service.
- `docs/push3-internals.md` "XMOS co-processor": the hub `0424:2534` is a USB mux. Switching Control -> Standalone makes the hub and the XMOS device leave the external host and enumerate on the compute module (`usb 1-1`, `usb 1-1.4`) within 3 s, with one disconnect and re-enumeration in between; `snd-usb-audio` loads at that moment. Evidence: device kernel log and the Mac's IOUSB tree before and after.
- `docs/push3-internals.md` launcher: `push3-launcher` polls `find_push3_live_port()` once per second (fails with "list index out of range" while tethered), restarts `Push3` after an exit 255 ("Couldn't find MIDI in port") and writes one telemetry line per minute: `T0=<C> T1=<C> LiveCPU=<%> PushCPU=<%> RootFree=<GB> DataFree=<GB>` to `/data/logs/launcher.log`.
- `docs/push3-internals.md` web service: `PushWebServiceCli` binds port 80, serves static pages from the Push's own install, and logs every listing and transfer with the peer address. Live's own device transfers are uploads through its `files/` routes. Pairing: `POST /api/v1/challenge` shows a six-digit code, `POST /api/v1/challenge-response {"secret":...}` returns a 64-character token, valid 30 days, sent back in the header `Ableton-Challenge-Response-Token`.
- `docs/push3-dsp-hosting.md`: Live's engine on the device reports ALSA, 44100 Hz, 128-sample input and output buffers, 10 input and 16 output channels, 8.71 ms overall latency (`Audio In Out` lines in Live's `Log.txt`). Live runs with `-_LinuxMidiBackend=Alsa` and `-DontLoadMaxForLiveAtStartup`.
